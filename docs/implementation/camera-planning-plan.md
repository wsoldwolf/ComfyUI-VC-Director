# カメラ計画の実装計画

状態: 実装・受入検証済み / 2026-10-25

結果は[カメラ計画の検証記録](camera-planning-validation.md)を参照。Python 105件、ブラウザ側11件、実Gemma4の30秒3Sceneと固定／追従指定、H3のCAMERA行だけを変えた16:9比較まで実行した。映像の構図変化を確認したが、終端の正面保持など細部のモデル遵守は保証できない。

## 目的と確認した問題

日本語シナリオから生成するSceneにカメラ計画を必ず持たせ、Scene EMDから最終H3プロンプトまで追跡できるようにする。固定カメラも明示した計画として扱う。人物が動くこととカメラが動くことを区別する。

対象はrun `vc_director_scenario_demo`、clip revision `5a6da231e90d4990ada2ff644ed5355c`。実行時アーカイブでは864×480・20ステップ、全3SceneのCAMERA指示が0件だった。比較した896×672の以前の出力にもCAMERA指示はなく、seedとプロンプトも異なる。背景特徴点による概算では以前の映像に約18%の拡大、今回にはほぼ固定の構図が見られた。16:9だけを原因とする証拠にはならない。

現在のDETAILはACTIONだけでも成功する。Compilerは存在するCAMERAを翻訳・結合できるが、不在のカメラ計画を創作しない。今回の変更は、この不足を計画コアで解消する。

## 採用する構成

```text
シナリオの方針・展開・参照画像の観察
  → Enhancer（作者の出来事と固定条件を保持）
  → TimelinePlanner outline（Scene構成・尺・接続）
  → TimelinePlanner detail（ACTION・CAMERA・DIALOGUE）
  → カメラ区間の検証／既存の有限再試行
  → Scene EMD保存
  → Compilerの既存処理でCAMERAを英訳・時刻変換
  → Context Loop / H3
```

- カメラの創作判断はGemma4とTimelinePlannerの責務にする。
- 初回実装では専用LLM呼出しを追加しない。既存のDETAIL応答へ組み込む。
- 既存のevent.kind=`camera`とCAMERA構文を使用し、Scene EMDのセクションや最終Planの形式を増やさない。
- Compilerによる自動カメラ追加、無指定時の一律ズーム、生成後の映像クロップによる移動演出は行わない。
- Context Loopは従来どおりScene全体を生成する。カメラ区間が複数あってもSampler実行や生成区間を増やさない。

## カメラの生成方針

1. 作者が方針・固定条件・展開に記述した固定／追従／パン等を優先する。既存の`* 方針:`と展開本文を使い、新しい必須入力は増やさない。
2. 指定がない場合は、動作と情景の目的に合わせてカメラを選ぶ。歩行には追従、視線の先を見せる場面にはパンやリフレーム、表情を読む場面には穏やかな寄り等を候補にする。
3. 『静かな短編映画』を全編固定カメラと同一視しない。意味のある場面では穏やかな移動を検討する。
4. 固定を選ぶ場合は『固定カメラ。画角と位置を保持する』等をCAMERAとして明記する。常に動かす割合や機械的な移動ローテーションは設けない。
5. 指示には対象・初期構図・移動方向／固定・速度・終端構図を簡潔に書く。『映画的に撮る』『人物を映す』だけで終えない。
6. 一つの区間では主要な撮影意図を一つに絞る。パン・回り込み・急ズーム等を無秩序に重ねない。顔・手・人物全体など、その場面の重要要素を見切らせない。
7. continueでは前Sceneの構図・方向を参考にし、作者が指定しない急な切り返しやハードカットを追加しない。人物なしのSceneはenvironmentを対象にする。
8. 台詞・人物の動作・音響許可をカメラ指示のために変更しない。歌唱向けの移植済みカメラ定型文は、短編の既定値へ流用しない。

## 生成と検証の契約

新しく生成する各Shotに、一件以上のCAMERAを要求する。複数のCAMERAがある場合はScene相対時刻で整列し、当該Shotの開始から終了まで隙間なく覆う。主要カメラ区間同士の重複は認めない。ACTIONやDIALOGUEとの時間的な重なりは許可する。

生成SchemaのprefixItemsを使い、Shotのeventsの先頭をCAMERAへ制約する。導入済みllama.cppはprefixItemsと辞書型itemsの併用時にprefixを無視するため、変換アダプターで先頭の固定部分と残りの反復部分を明示的なGBNFへ変換する。残りのeventsには既存のACTION・CAMERA・作者のDIALOGUEを許可する。カメラを先頭へ置くことは表示・生成上の規則であり、他eventとの時間的な前後関係を意味しない。

JSON Schema／GBNFだけではShotのstart/endとevent区間の一致を保証できないため、意味検証を併用する。`core/planner/camera.py`へ、少なくとも次の検査を集約する。

| 診断 | 条件と修正内容 |
|---|---|
| CAMERA_MISSING | ShotにCAMERAがない。固定を含む具体的なカメラ指示を要求する |
| CAMERA_COVERAGE | Shotの途中に空白がある。必要な開始・終了値を数値で示す |
| CAMERA_OVERLAP | 主要カメラ区間が重なる。競合IDと区間を示す |
| 既存event検証 | Shot外の時刻、長さ0、出演者外の対象、発声・BGM指示等を拒否する |

新しい検査はTimelinePlannerのDETAIL用checkから呼ぶ。StageRunnerのキャッシュ読込時・初回応答・修正応答の全てで検査し、既存の最大3回の試行に含める。別枠の無制限リトライやPythonによる内容補完は追加しない。自然文の『本当に追従を表すか』をキーワードだけで断定する検査は初回には設けず、実LLM出力とH3で評価する。

### 既存構文による出力例

以下は10秒Scene内の一つのShotに属するCAMERAの例。ACTION・DIALOGUE等の行は省略している。

```markdown
### Shot sh_return 00:00.000 --> 00:10.000
* CAMERA cam_follow 00:00.000 --> 00:04.000 | @hero | 中景から主人公の横移動をゆっくり追従し、上半身と進行先を画面に残す。
* CAMERA cam_hold 00:04.000 --> 00:07.000 | @hero | 主人公が足を止めた位置でカメラも停止し、墓石と表情が読める中景を保持する。
* CAMERA cam_pan 00:07.000 --> 00:10.000 | environment | 主人公の視線に沿って遠くの家へゆっくりパンし、終端では家を構図の中心へ収める。
```

## 変更箇所と実装順序

| 順序 | 対象 | 変更 |
|---|---|---|
| 1 | `core/planner/camera.py`、Plannerテスト | CAMERAの有無・時間被覆・重複を検証する関数と境界ケースを実装 |
| 2 | `core/protocols/llm.py` | DETAILの生成SchemaへCAMERA先頭の制約を追加し、既存GBNF変換で有効なJSONになることを確認 |
| 3 | `prompts/story_detail_prompt.txt`、`core/planner/api.py` | カメラ選択・具体化・静止指定・接続継続を指示し、DETAILのcheckへ検査を組み込む |
| 4 | DETAIL prompt version | カメラ必須化に合わせて更新。Enhancer／outlineの成功cacheは維持 |
| 5 | EMD／Compiler回帰テスト | CAMERAの時刻・対象・方向・native Subject割当が英訳後のPlanへ残ること、台詞と音響方針が変わらないことを確認 |
| 6 | 仕様・操作文書 | 新規生成時のカメラ必須、固定カメラ、既存保存物の互換、確認箇所を明記 |
| 7 | 実Gemma4／H3検証 | 固定シナリオのカメラ計画と、条件を揃えた短区間比較を実施 |

## 互換性と再生成

- CAMERA必須は新しいPlanner生成経路へ適用する。共通のScene SchemaやCompilerへ無条件の必須制約を足し、過去の保存revisionを読み込めなくする変更は避ける。
- `saved_scene`の手書きEMD・既存Planは従来どおり読込・コンパイルできる。既存ファイルへのCAMERAの追記は自動で行わない。
- 新しいカメラ計画を使うには言語生成から新revisionを保存する。動画生成モードへ切り替えるだけでは、旧Planへカメラは追加されない。
- 新revisionやカメラ指示の変更は既存fingerprintへ反映させ、旧動画を新しい生成の成功結果として再利用しない。比較用動画は別run名で保存する。

## 受入検証

### CPU・固定応答

- 固定・追従・パン・人物なし・複数Shot・continueの各ケースを検証する。
- CAMERAなしの応答を成功扱いせず、具体的な修正要求で回復できることを確認する。修正に失敗したら既存の診断ログを残し、失敗を通知する。
- 先頭／終端の空白、途中の空白、重複、0長、Shot外の区間を検出する。
- 旧revisionの読込、旧Scene EMDの往復、保護された台詞、音響禁止、Context Loop時刻変換の回帰テストを通す。

### 実Gemma4

- 既存の墓地→門→居間の30秒シナリオを使う。入力・モデル・runtime・seedを記録し、各Shotに具体的なCAMERAが生成されることを確認する。
- 『固定カメラで撮る』と『歩行に追従する』を明記した別ケースを評価し、固定も移動も指定どおり計画できることを確認する。
- `scenes.emd`、`plan.json`、実行アーカイブの3箇所でCAMERAの内容と時刻を照合する。

### H3の比較

最初に864×480・20ステップで、同じseed・参照素材hash・モデル合成・Sampler・高速化設定・台詞・音響・人物動作を保ち、CAMERA行の有無だけを変えた比較を行う。LLMの再生成で他の文章まで変えたPlan同士を、この比較の代用にしない。カメラ追加に必要な翻訳以外の文面も固定する。

次に必要に応じ、同じCAMERA付きプロンプトを16:9と4:3で比較する。目標MPを揃え、丸め後の実寸も記録する。seed固定でも解像度変更後のノイズ配置まで同一にはならないため、単一seedから一般的な画角特性を断定しない。

背景特徴点の移動・拡大と目視を併用し、人物の移動をカメラ移動と誤認しない。推定値だけを画質の優劣に置き換えない。H3によるカメラ指示の遵守は確率的であり、計画・転送の成功と映像上の実現を別々に記録する。Spectrumのreplay中止は既知の別件として、各比較で状態を記録する。

実生成中のユーザージョブは中断せず、検証は空き状態で別runへ実行する。上記の実装と検証が終わるまで、カメラ制御の改善完了とは扱わない。
